  - Rule 1 — koi apne access ke bahar ka data na dekhe. Local A ka data Local B

  - 22,400 ek local mein (ek callout sab ko) → synchronous send impossible
  - push ka 5–10% silently fail → retry lazmi, aur retry safe hona chahiye

  2. Part A ke 4 sawal — Django/DRF/Postgres mein soch

  Q1 — Data model (sab se important decision yahin hai)

  Jo table brief ne deliberately chhoda hai woh hai per-recipient record.
  announcements table sirf message hai; tumhe ek "recipients/deliveries" table
  chahiye:

  announcement_recipients
    id               uuid
    announcement_id  uuid -> announcements
    member_id        uuid -> members
    delivery_state   text   -- pending | sent | failed
    read_at          timestamptz   -- null = nahi parha
    acked_at         timestamptz   -- null = acknowledge nahi kiya
    rsvp             text   -- null | coming | cant
    UNIQUE(announcement_id, member_id)   <-- yeh line Rule 2 ki jaan hai

  Key design insight jo reviewer dhoondh raha hai: "nothing / read /
  acknowledged / coming / can't" ko ek single status enum mein mat thoso. Yeh
  orthogonal dimensions hain:
  - delivery_state = machine ka view (bheja ya nahi)
  - read_at = member ne khola
  - acked_at = member ne confirm kiya (sirf jab needs_ack)
  - rsvp = coming/can't

  Ek member bina ack kiye parh sakta hai, bina RSVP kiye ack kar sakta hai.
  Single enum mein yeh impossible orderings ban jaati hain aur information loss
  hoti hai. Separate columns/timestamps = mature design. Isko DESIGN.md mein
  explicitly justify karna.

  Scale note: 22,400 rows per bada announcement — yeh theek hai (fan-out on
  write). Dhyan: index on (announcement_id, delivery_state) taake counts aur
  retries fast hon.

  Q2 — The send path (14:02 pe Send dabaya)

  Yeh sabse galat jagah hai jahan log synchronous loop likh dete hain. Sahi
  tasveer:

  Synchronous request (leadership ~50–200ms wait karti hai):
  1. Permission check — yeh banda is local ka leadership hai? (Rule 1)
  2. announcement row ko sending state mein daalo (ya sent_at set karo)
  3. Ek Celery job enqueue karo
  4. 202 Accepted return — bas. Leadership 22,400 pushes ka intezaar NAHI karti.

  Async (Celery worker, background):
  1. Recipients materialize karo ek SQL statement se: INSERT INTO
     announcement_recipients (...) SELECT ... FROM members WHERE local_id = X
     AND status = 'active' ON CONFLICT DO NOTHING — 22,400 inserts loop mein
     nahi, ek bulk statement.
  2. Phir push dispatch batches mein (e.g. 500 at a time), har batch ke baad
     counter update.

  Counts polling wala sawal (4 log status screen khole counts dekh rahe — DB har
  second kyun na hammer ho?):

  Ghalat: har poll pe COUNT(*) ... GROUP BY delivery_state 22,400 rows pe × 4
  clients × har second.

  Sahi: denormalized counters announcements row pe (sent_count, read_count,
  acked_count), jo events pe incrementally update hote hain (ack aaya → atomic
  UPDATE ... SET acked_count = acked_count + 1; fan-out batch → += 500). Status
  endpoint sirf ek single-row read karta hai. Upar se Redis cache with 2–5s TTL
  laga do — ab 4 client hon ya 40, DB pe per window ek hi hit. (Websockets/SSE
  mention kar sakte ho but polling + cached counter kaafi aur simple hai.)

  Q3 — Do rules, by design (yahan sabse zyada marks hain)

  Rule 1 — do boundaries:

  - Boundary A (local ↔ local): har query local_id se scope honi chahiye.
  - Boundary B (member ↔ leadership): member send/other-members-ka-data access
    na kar sake.

  Pehle identity model karo (brief ne jaan boojh ke chhoda): Django User ko ek
  member/account se link karo, with role (member | leadership) aur local_id.
  Authenticated principal ka local_id = scoping key.

  "Agle saal koi naya endpoint banaye aur filter lagana bhool jaye to?" — yeh
  sawal tumhe per-view manual .filter(local_id=...) se door le jaata hai. Ek
  bhool = leak. Robust jawab structural / fail-closed hai:

  - Postgres Row-Level Security (RLS) — strongest answer. Har request pe session
    variable set karo (SET app.current_local = ...), tables pe RLS policy
    local_id pe. Ab agar view mein filter bhool bhi jao, database khud
    cross-local rows return nahi karega. Yeh seedha "someone forgets next year"
    ko address karta hai.
  - Plus DRF: ek base ViewSet + base Permission class jo scoping aur role by
    default enforce kare — naye endpoints inherit karein. Safe cheez ko default
    banao.

  Apprentice contact info wala concern khud hal ho jaata hai: agar query level
  pe scoping hai, doosre local ke members load hi nahi hote, serialize karne ka
  sawal hi nahi.

  Rule 2 — exactly-once (NOT "button disable"):

  Teen layers, sab shared state (DB) mein — app memory mein nahi:
  1. UNIQUE(announcement_id, member_id) + ON CONFLICT DO NOTHING → restart
     dubara insert chalaye to duplicate rows banti hi nahi.
  2. Per-recipient state machine: worker sirf pending rows claim karta hai
     (SELECT ... FOR UPDATE SKIP LOCKED), transaction mein sent karta hai.
     Restart ke baad sirf bachi hui pending rows uthti hain — pehle bheji hui
     skip.
  3. Announcement-level idempotent send: created → sending transition sirf ek
     dafa. Leader ne retry maara aur already sending/sent hai → no-op.

  Iska matlab Rule 2 ko DB constraints "sach" banati hain, app logic akeli nahi.

  Production mein kaise pata chale ke rule pehle se toot chuka hai:
  - Rule 1: reconciliation query jo hamesha 0 return karni chahiye —
    recipient.member.local_id != announcement.local_id wali rows. Plus
    permission-denial / cross-local access ka audit log + alert.
  - Rule 2: har actual push dispatch ko log karo with recipient_id; metric
    pushes_sent vs distinct recipients. Diverge ho to alert.

  Q4 — Diagram

  Boxes: Clients → Load Balancer (nginx/HAProxy) → {Django instance 1, instance
  2} → Postgres + Redis, aur Celery workers jo broker (Redis/RabbitMQ) se jobs
  lekar Push provider ko call karte hain.

  Yahan load balancer ka asli point: do instances round-robin. Agar "have we
  already sent this" check kisi process ki in-memory set/dict mein hota, to
  doosra instance uska state nahi dekhta → double send. Isi liye Rule 2 ka
  source of truth Postgres (unique + state) hona chahiye, process memory nahi.
  Yeh exactly woh cheez hai jo brief ke DevOps bonus mein poochi gayi hai —
  build karo ya na karo, interview mein zaroor poochenge.

  Sab se important takeaways (yeh 5 cheezein design ko bana ya bigaad deti hain)

  1. Recipients table + UNIQUE(announcement_id, member_id) — missing table yahi
     hai, aur Rule 2 ki buniyad.
  2. Send async hai — request sirf intent record + enqueue karti hai, 202
     return.
  3. Rule 1 structural enforcement (RLS / base viewset), per-view filter
     discipline nahi — kyunke log bhoolte hain.
  4. Rule 2 shared state (DB) mein, process memory mein nahi — warna 2 instances
     pe toot jaata hai.
  5. Counts = denormalized counters + cached read, GROUP BY scan nahi.

❯ 22,400 ek local mein (ek callout sab ko) → synchronous send impossible

  ye possible kese ho?

⏺ Achha sawal — yeh design ka core mental shift hai. Chalo pehle dekhte hain
  synchronous kyun fail hota hai (numbers se), phir kaise possible banta hai.

  ---

  Pehle: synchronous kyun impossible hai

  Jab leadership "Send" dabati hai, agar tum usi HTTP request ke andar 22,400
  pushes bhejne ki koshish karo:

  Har push ek external network call hai (FCM/APNs ko), maano ~100ms. Loop mein:

  22,400 × 100ms = 2,240 seconds ≈ 37 minutes

  Ab masle:
  - Timeout — nginx/load balancer typically 30–60s mein request kaat deta hai.
    Browser bhi. 37 min koi wait nahi karega.
  - Worker block — Gunicorn/uWSGI ka ek worker 37 min ke liye phansa reh jata
    hai. Us dauran woh worker kisi aur request ko serve nahi kar sakta. Chand
    bade sends = saare workers khatam = poora app dead.
  - Crash = sab barbaad — agar beech mein process gir gaya (deploy, OOM), to jo
    bheja woh bhi track nahi, kahan ruke pata nahi. Retry karo to double
    delivery (Rule 2 toot gaya).

  Yani request ke andar yeh kaam karna structurally galat hai. Timeout aur
  resource dono maar denge.

  ▎ Note: DB wala hissa fast hai — 22,400 recipient rows ek INSERT ... SELECT se
  ▎ banana sub-second kaam hai. Qatil external push calls hain, DB nahi.

  ---

  Ab: possible kaise banta hai — "receipt do, kaam baad mein"

  Core idea: request ko kaam poora nahi karna — sirf kaam record karke receipt
  deni hai.

  Step 1 — Synchronous request (tez, ~100ms)

  Leadership "Send" dabati hai
    → permission check (Rule 1)
    → announcement row ko `sending` state mein daalo
    → ek Celery job enqueue karo (broker: Redis/RabbitMQ)
    → 202 Accepted return  ← yahin request khatam
  Leadership ko lagta hai "bhej diya" — woh status screen pe counts dekhne lag
  jaati hai. 22,400 pushes abhi start bhi nahi hue.

  Mental model: 202 ka matlab "result" nahi, "maine le liya, process kar raha
  hoon" (receipt). Jaise courier parcel leta hai — delivery baad mein, par tumhe
  slip ab mil gayi.

  Step 2 — Background worker fan-out karta hai (Celery)

  Enqueue hua job worker pick karta hai (request se alag process, timeout nahi):

  1. Recipients materialize:  INSERT INTO announcement_recipients
       SELECT ... FROM members WHERE local_id = X AND status='active'
       ON CONFLICT DO NOTHING          ← 22,400 rows, ek statement
  2. Phir chunks mein push dispatch — 500 at a time

  Step 3 — Parallelism (yahan "37 min" ghat ke minute ban jate hain)

  Fan-out task khud ko chhote sub-tasks mein tod deta hai, har ek batch ko alag
  worker chalata hai:

  22,400 recipients → 45 batches × 500
  45 batches ÷ 10 workers chalte parallel
  → ~37 min ka kaam ab ~4 min mein
  Aur workers barhao → aur tez. Yeh horizontal scaling hai — request ke andar
  yeh mumkin hi nahi tha.

  Step 4 — Resumable + idempotent (crash-safe)

  Har recipient row ka ek delivery_state hai. Worker sirf pending rows claim
  karta hai:

  SELECT ... FROM announcement_recipients
  WHERE announcement_id = X AND delivery_state = 'pending'
  FOR UPDATE SKIP LOCKED
  LIMIT 500;
  -- push bhejo, phir in rows ko 'sent' kar do (same transaction)

  - Crash ho gaya beech mein? Restart pe worker sirf bachi hui pending rows
    uthata hai — jo sent ho chuki skip. Resume ho jata hai.
  - UNIQUE(announcement_id, member_id) + state guard = retry ya restart pe
    dobara delivery nahi (Rule 2).
  - 5–10% push silently fail? Jo fail hui unko pending/failed rakho, sirf unhein
    retry karo — safely.

  ---

  Poori timeline ek nazar mein

  14:02:00.000  Leadership "Send" dabati hai
  14:02:00.120  202 Accepted → UI "sending..." dikhata hai   [request khatam]
  14:02:00.5    Worker recipients bulk-insert karta hai (22,400 rows)
  14:02:01      45 batches enqueue; 10 workers parallel push bhejte hain
  14:02:01–14:06  phones buzz hote rehte hain; counts barhte rehte hain
  14:03:30      ek worker crash → restart → bachi pending rows uthayi   [double
  send nahi]
  14:06:00      saari pending → sent; status screen "22,400 sent" dikhata hai

  Leadership ne 120ms wait kiya, 37 min nahi. Asli kaam background mein chalta
  raha, resumable aur exactly-once.

  ---

  Khulasa: "synchronous impossible" ka jawab yeh nahi ke 22,400 pushes nahi bhej
  sakte — balke yeh ke unhe request ke andar nahi bhejte. Request intent record
  karti hai aur receipt (202) deti hai; Celery workers background mein, chunked
  + parallel + resumable tareeke se asli fan-out karte hain; UI alag se counts
  poll karti hai.

  Agle step pe chaho to dekhein: worker ke andar exact state machine (pending →
  sent → failed/read/acked), ya status counts wala cached-counter design. Kahan
  chalein?

❯ FCM/APNs sa acha se possible hoga ya celery se?

⏺ Yahan ek choti si confusion clear kar deta hoon, kyunke yeh samajhna zaroori
  hai: FCM/APNs aur Celery competitors nahi hain — yeh do alag layers hain jo
  mil ke kaam karte hain. "Yeh ya woh" wala sawal nahi banta.

  ---

  Dono ka kaam alag hai

  ┌────────────┬─────────────────────────────────┬──────────────────────────┐
  │            │             Celery              │        FCM / APNs        │
  ├────────────┼─────────────────────────────────┼──────────────────────────┤
  │ Kya hai    │ Background job runner (tumhara  │ Push delivery service    │
  │            │ code chalata hai)               │ (Google/Apple ka)        │
  ├────────────┼─────────────────────────────────┼──────────────────────────┤
  │ Kaam       │ Orchestration — kab, kitne      │ Notification ko asal     │
  │            │ batch, parallel, retry, resume  │ phone tak pohnchana      │
  ├────────────┼─────────────────────────────────┼──────────────────────────┤
  │ Kahan      │ Tumhare server pe               │ Google/Apple ke servers  │
  │ chalta     │                                 │ pe                       │
  ├────────────┼─────────────────────────────────┼──────────────────────────┤
  │ Tum kya    │ task likhte ho                  │ uski API call karte ho   │
  │ karte ho   │                                 │                          │
  └────────────┴─────────────────────────────────┴──────────────────────────┘

  Yeh ek doosre ki jagah nahi lete. Celery worker hi FCM/APNs ko call karta hai.
  Celery = "kaam ka manager", FCM/APNs = "delivery truck".

  ---

  Layering (kaun kisko call karta hai)

  Leadership "Send"
        │
        ▼
  Django request  ──enqueue──►  Celery worker (background)
                                     │  batch of 500 recipients
                                     │  har recipient ke liye:
                                     ▼
                                FCM / APNs API call   ◄── yeh asal push
  transport
                                     │
                                     ▼
                                Member ka phone (OS notification dikhata hai)
                                     │
                                     ▼
                         Member app kholta hai → read/ack
                                     │
                                     ▼ (yeh wapas TUMHARE API pe aata hai, FCM
  se nahi)
                                Django  → recipient row update (read_at /
  acked_at)

  Celery ke bagair: tumhare paas FCM ko 22,400 dafa, chunked, parallel,
  resumable, exactly-once call karne ka koi tareeqa nahi — woh orchestration
  Celery deta hai.

  FCM ke bagair: Celery ke paas phone tak pohnchne ka koi raasta nahi — woh
  transport FCM/APNs deta hai.

  ---

  Ek aur baareek baat — delivery ki do sarhadein

  1. Tumhara backend → FCM: yeh tumhare control mein hai. Celery call karta hai,
     response milta hai (accepted/failed). Isko tum delivery_state mein record
     karte ho.
  2. FCM → phone: yeh FCM best-effort karta hai. Member basement/underground
     mein offline hai to FCM thodi der hold karega (TTL), phir chup chaap fail
     (woh 5–10% yahin). FCM "din bhar" reliably hold nahi karta.

  Isi liye design mein source of truth push nahi, tumhari recipient row hai.
  Member jab ghanton/dinon baad online aata hai, app khol ke message pull (read
  via API) karta hai — chahe push kabhi aaya ho ya na aaya. Push sirf "tap pe
  jagao" hai; asal message DB mein baitha hai.

  Is exercise ke liye khaas baat

  Brief saaf keh raha hai (page 4):

  ▎ "Real push notifications are not required. Log them, or write them to a
  ▎ table. Nobody needs FCM credentials for this."

  Yani build mein FCM/APNs lagana hi nahi. Tumhara Celery worker "push bhejne"

  abhi mock/log kar raha hoon." Celery phir bhi chahiye — woh tumhari apni
  machinery hai, mock karne wali nahi.

  ---

  Khulasa: sawal "FCM/APNs se ya Celery se?" nahi banta — Celery woh cheez hai

⏺ Yeh Rule 2 ka dil hai. Core idea ek line mein: "kisko bhej diya" ka record DB
  ki row mein hai, kisi process ki memory mein nahi. Retry/restart dubara wahi
  row dekhta hai aur "yeh to ho chuka" samajh ke skip kar deta hai.

  Chalo tod ke dekhte hain.

  ---

  1. Har recipient ki ek row = ledger (register)

  announcement_recipients
    announcement_id  uuid
    member_id        uuid
    delivery_state   text   -- pending | sending | sent | failed
    UNIQUE(announcement_id, member_id)

  Shuru mein har row pending. Worker push bhejta hai to sent kar deta hai. Ab jo
  bhi dekhega, sent rows ko chhod dega. Yeh row hi "yaddasht" hai — crash ho,
  restart ho, worker badal jaye, yaddasht DB mein mehfooz.

  ---

  2. Teen retry scenarios, teeno DB se handle

  (a) Worker crash ho ke restart hua (beech send mein)
  Restart pe worker sirf yeh query chalata hai:
  ... WHERE announcement_id = X AND delivery_state = 'pending'
  Jo rows pehle sent ho chuki — is query mein aati hi nahi. Toh unko dobara nahi
  bheja jata. Sirf bachi pending complete hoti hain. Resume + no-double, dono.

  (b) Leadership ne "stuck" samajh ke Send dobara dabaya
  Yeh announcement level pe rok do. announcements.state khud ek guard hai:
  UPDATE announcements SET state = 'sending'
  WHERE id = X AND state = 'created'   -- sirf 'created' se 'sending' ja sakta
  RETURNING id;
  Agar 0 rows return — matlab already sending/sent hai → dusra fan-out start
  hota hi nahi. Ek hi dafa recipients banenge.

  (c) Push 5–10% silently fail hui, unko retry karna hai
  Failed rows failed (ya wapas pending) rehti hain. Retry sirf unhi ko uthata
  hai — sent ko haath nahi lagata. Safe retry.

  ---

  3. Lekin asli trap: do worker ek hi row na uthayein (race condition)

  Naive code toot jata hai:
  rows = SELECT * WHERE state='pending'   # Worker A aur B dono SAME rows parh
  lete hain
  for r in rows:
      send_push(r)                         # dono bhej dete hain → DOUBLE
      UPDATE r SET state='sent'

  Dono workers ek hi pending rows dekh lete hain → dono push bhej dete hain.
  Yahan DB constraint kaafi nahi, atomic claim chahiye:

  BEGIN;
  SELECT id FROM announcement_recipients
    WHERE announcement_id = X AND delivery_state = 'pending'
    FOR UPDATE SKIP LOCKED      -- yeh rows lock; dusra worker inhe SKIP kar ke
  alag rows le
    LIMIT 500;
  -- (push bhejo) phir:
  UPDATE ... SET delivery_state = 'sent' WHERE id IN (...);
  COMMIT;

  FOR UPDATE → rows lock. SKIP LOCKED → dusra worker locked rows ko chhod ke
  alag pending rows uthata hai. Isi liye do worker kabhi ek hi member ko nahi
  bhejte. Yeh Postgres ka built-in trick hai, is kaam ke liye banaya gaya.

  ---

  4. UNIQUE constraint = aakhri deewar

  UNIQUE(announcement_id, member_id)

  Agar galti se fan-out dubara chala aur recipients dobara banane lage:
  INSERT INTO announcement_recipients (...)
  SELECT ... FROM members WHERE local_id = X
  ON CONFLICT (announcement_id, member_id) DO NOTHING;
  ON CONFLICT DO NOTHING → jo rows pehle se hain, dobara nahi banti. Database
  khud duplicate row banne hi nahi deta. Code mein bug ho tab bhi — DB
  fail-closed.

  ---

  5. Ek imandar baareeki (crash-mid-push)

  Ek chhota window hai: push bhej diya, par sent mark karne se pehle hi crash.
  Do raaste:
  - Pehle mark, phir push → crash ho to dobara nahi bhejta (no double), par woh
    ek member us push ko miss kar sakta hai.
  - Pehle push, phir mark → crash ho to dobara bhej dega (possible double).

  Rule 2 "no double" ko zyada weight deta hai, toh "pehle mark" wala bias
  behtar. Aur jo member woh ek push miss kare — uska message phir bhi uski
  recipient row mein baitha hai. Jab woh basement se nikal ke app kholega, woh
  message pull (read via API) kar lega. Push sirf "jagao" hai; asal message DB
  mein mehfooz hai. Is liye ek dropped push permanent miss nahi banta.
